# API історії викликів (Call History)

**Ендпоінти:** `SearchHistoryCall` (GET) та `SearchHistoryCallPost` (POST) — пошук завершених викликів (CDR) у `cc_calls_history`.

> **Умовні позначки.** Усі часові мітки — Unix epoch у **мілісекундах (UTC)**, усі `*_sec` — тривалості в **секундах**. Діапазони `FilterBetween` задаються як `{ "from": …, "to": … }` і є **включними** (`from ≤ значення ≤ to`).
>
---

## 1. Довідник API (Reference)

### 1.1. Огляд ендпоінта

| Властивість | Значення |
|---|---|
| RPC-методи | `SearchHistoryCall`, `SearchHistoryCallPost` |
| gRPC-сервіс | `engine.CallService` (пакет `engine`) |
| HTTP-мапінг (GET) | `GET /calls/history` — фільтри у query-параметрах |
| HTTP-мапінг (POST) | `POST /calls/history`, `body: "*"` — фільтри у JSON-тілі |
| Тип запиту / відповіді | `SearchHistoryCallRequest` → `ListHistoryCall` |
| Побічні ефекти | Немає (операція лише для читання, безпечна для повторів) |
| Обов'язкова умова | Має бути задано **хоча б один** із фільтрів: `created_at`, `stored_at`, `number`, `q`, `dependency_id` або `id`. Інакше — `400` (див. [1.3](#обовязкова-умова-пошуку)) |
| Автентифікація | Токен авторизаційної сесії у заголовку `X-Webitel-Access: <token>` |
| `Content-Type` | `application/json` (для POST) |

**Коли використовувати POST.** Варіант POST має ту саму семантику, що й GET, але підходить для великих списків ідентифікаторів, мапи `variables` та інших фільтрів, які можуть перевищити ліміт довжини URL.

**Кодування параметрів у GET** (стандартне для grpc-gateway):

- масиви — повторення параметра: `queue_id=12&queue_id=13`;
- діапазони — через крапку: `created_at.from=1790640000000&created_at.to=1790726399999`;
- мапа `variables` — формат `map_name[key]=value`, наприклад `variables[campaign]=autumn_sale` (у cURL використовуйте `-g` / `--globoff` або кодуйте дужки);
- `BoolValue` — `has_file=true` / `has_file=false`; відсутній параметр означає «не фільтрувати»;
- сортування — `sort=-created_at` (за спаданням) або `sort=%2Bcreated_at` (за зростанням): символ `+` в URL необхідно кодувати як `%2B`, інакше він буде інтерпретований як пробіл.

### 1.2. Права доступу та RBAC

#### Послідовність обробки

1. **Валідація (API-шар).** Перевіряється наявність хоча б одного «якірного» фільтра (див. [1.3](#обовязкова-умова-пошуку)). Якщо його немає — `400 Bad Request`.
2. **Часове обмеження історії для time-limited доступу до записів (API-шар).** Якщо в користувача немає повного доступу до записів (`accessFiles = false`; див. крок 5), але є дія `time_limited_record_file` (`PermissionTimeLimitedRecordFile`), береться системне налаштування домену `period_to_playback_records` (кількість днів). Тоді `showFileFromDate = зараз − N днів`, а нижню межу `created_at.from` піднімають до цієї дати (за відсутності `created_at` фільтр створюється). Такий користувач бачить історію лише за останні N днів, а файли показуються для всіх викликів вибірки. Якщо налаштування не задано, обмеження за часом не діє, але файли також не повертаються. Саме це — найчастіша причина, чому відповідь коротша за очікувану.
3. **Перевірка права читання.** Для сесії перевіряється дозвіл `PERMISSION_SCOPE_CALL` (клас `calls`) з доступом `read`. Якщо його немає — повертається `403 Forbidden` (`api.context.permissions.app_error`).
4. **Вибір режиму доступу.** Якщо для цього дозволу діє RBAC (`session.UseRBAC`), пошук виконується в режимі **обмеження за групами/ролями** (`GetHistoryCallPageByGroups`). Інакше — у режимі **повного доступу до домену** (`GetHistoryCallPage`).
5. **Фільтрація файлів у відповіді.** Незалежно від режиму з поля `files` вилучаються:
    - записи екрана (`channel = screen_recordings`), якщо немає права читання `PermissionScreenRecordings`;
    - файли відеодзвінків, якщо немає права читання `PermissionVideocallFiles`.

    Окрім цього, поля `files` та `files_job` повертаються лише якщо виконується одна з умов: (а) користувач має повний доступ до записів (`accessFiles`: дія `PermissionRecordFile` або RBAC-читання цього дозволу); (б) діє часове обмеження з кроку 2 і виклик створено пізніше за `showFileFromDate` (на практиці — усі виклики вибірки). В інших випадках обидва поля порожні.
6. **Маскування номерів (API-шар).** Якщо в сесії немає дії `view_cdr_phone_numbers` (`PermissionViewNumbers`), маскуються значення полів `destination`, `from.number` та `to.number`:
    - середня частина рядка замінюється символами `X`, початок (`pref`) та кінець (`suff`) залишаються видимими; мінімальна довжина, `pref` і `suff` задаються налаштуваннями сервісу;
    - маскування застосовується лише за одночасного виконання умов: довжина значення > мінімальної довжини, довжина > `pref + suff + 1` і мінімальна довжина ≥ `pref + suff + 1`. Інакше (короткий номер або конфігурація, що не задовольняє умову) значення повертається **без змін**;
    - приклад (умовні параметри: мінімальна довжина 8, `pref` = 3, `suff` = 2): `380501234567` → `380XXXXXXX67`;
    - **виняток** — оператор переглядає власні пропущені: одночасно `user_id = [власний ID]`, `missed = true` і `cause = ["NO_ANSWER", "ORIGINATOR_CANCEL"]` (саме в такому порядку); тоді номери не маскуються.

> **Важливо.** Виклики, що виходять за межі доступу користувача, **не спричиняють помилки 403** — вони просто не потрапляють до вибірки. Помилка `403` виникає лише за відсутності базового права `calls:read`.

> **Примітка.** Авторизація виконується внутрішньою системою дозволів: об'єкт `calls` (`PERMISSION_SCOPE_CALL`), рівень доступу `read` (скорочено — `calls:read`).

#### Мультитенантність (`domain_id`)

- Кожен SQL-запит містить умову `domain_id = :Domain` — дані різних доменів ізольовані.
- В обох режимах (RBAC і повний доступ) домен береться **виключно з авторизаційної сесії**. Метод `session.Domain(...)` є звичайним геттером домену сесії, а переданий йому параметр не використовується.
- Значення `domain_id` у запиті **ігнорується**: отримати дані іншого домену неможливо.

#### Правила видимості в режимі RBAC

Виклик видимий користувачеві, якщо виконується **хоча б одна** умова (логіка OR):

| № | Умова | Пояснення |
|---|---|---|
| 1 | `user_id` виклику ∈ (`cc_calls_rbac_users` ∪ ролі користувача) | Виклик належить користувачеві з «підконтрольної» множини або користувачеві, який входить до ролі |
| 2 | ID поточного користувача ∈ `user_ids` виклику | Користувач брав участь у будь-якому плечі виклику |
| 3 | `user_ids` виклику перетинається з (`cc_calls_rbac_users` ∪ ролі) | У виклику брав участь хтось із підконтрольної множини |
| 4 | `queue_id` ∈ `cc_calls_rbac_queues(...)` | Виклик оброблено в черзі, до якої користувач має доступ (див. «Доступ до черг» нижче) |
| 5 | `user_ids` перетинається з `rbac_users_from_group('calls', domain, read, ролі)` | Доступ, наданий через ACL за замовчуванням (див. «Доступ через ACL ролей» нижче) |
| 6 | `grantee_id` виклику ∈ ролі користувача | Виклик виконано від імені суб'єкта (grantee), яким володіє роль користувача |

**Підконтрольна множина користувачів** (`cc_calls_rbac_users`) складається з користувачів-агентів, які відповідають хоча б одній умові:

- сам користувач (якщо він є агентом);
- агенти, у яких поточний агент указаний у `supervisor_ids`, **за умови** що він має ознаку `supervisor`;
- агенти, у яких користувач указаний як аудитор (`auditor_ids`);
- агенти команд, де поточний агент є адміністратором команди (`team.admin_ids`).

Якщо користувач не є агентом, ця множина порожня, і доступ визначається лише ролями (умови 5–6) та чергами (умова 4).

#### Доступ до черг (`cc_calls_rbac_queues`)

Функція повертає об'єднання двох наборів черг:

1. **Черги за навичками (skills).** Береться «коло» агентів користувача: він сам (якщо є агентом), агенти, у яких він указаний у `supervisor_ids` (перевіряється ознака `supervisor` запису агента), та агенти команд, де він адміністратор (`team.admin_ids`). З цього кола залишаються **лише агенти, для яких користувач є аудитором** (`auditor_ids`). Для таких агентів беруться їхні ввімкнені навички, а далі — ввімкнені черги, що потребують цих навичок, за умови що рівень навички (`capacity`) лежить між `min_capacity` і `max_capacity` черги.
2. **Черги за роллю.** Усі черги домену, у яких `grantee_id` належить до ролей користувача.

> Наслідок: супервайзер, який не є аудитором, **не** отримує доступ до черг за навичками; він бачить виклики своїх агентів через умови 1–3, а виклики черг — лише якщо черга належить його ролі.

#### Доступ через ACL ролей (`rbac_users_from_group`)

Функція повертає користувачів — мемберів ролей (`wbt_auth_member`), які є власниками (`grantor`) у ACL за замовчуванням (`wbt_default_acl`) для класу `calls` цього домену, де суб'єктом (`subject`) виступає одна з ролей поточного користувача, а маска доступу містить `read`. Інакше кажучи: якщо роль користувача має право читання на виклики, створені мемберами певної ролі, користувач бачить виклики цих мемберів.

#### Поведінка залежно від типу доступу

| Тип доступу | Що бачить користувач |
|---|---|
| Роль без RBAC-обмеження на `calls:read` (як правило, адміністратор) | Усі CDR свого домену |
| Супервайзер (`supervisor = true`) | Власні виклики та виклики агентів, яких він курирує, плюс виклики черг і ролей за умовами 4–6 |
| Аудитор | Виклики агентів, де він указаний аудитором, та виклики черг за навичками цих агентів |
| Адміністратор команди | Виклики агентів своїх команд |
| Агент / оператор | Лише виклики, у яких він бере участь (`user_id` / `user_ids`), плюс виклики за ролями та чергами, якщо вони йому надані |

> Назви ролей умовні: фактичний доступ визначається налаштуваннями дозволів і зв'язками агент–команда–супервайзер, а не фіксованими назвами.

### 1.3. Параметри запиту

Окремо жоден параметр не є обов'язковим, але запит має містити [хоча б один «якірний» фільтр](#обовязкова-умова-пошуку). Фільтри поєднуються за логікою **AND**; елементи масивів усередині одного фільтра — за логікою **OR**. Порожній масив, порожній рядок або `0`/відсутнє значення означають «фільтр не застосовується».

#### Обов'язкова умова пошуку

Запит приймається лише якщо задано **хоча б один** із параметрів: `created_at`, `stored_at`, `number`, `q`, `dependency_id` або `id`. Інакше повертається `400` / `InvalidArgument` (id `grpc.call.search_history`, повідомлення `filter created_at or stored_at or q is required`). У таблицях нижче такі параметри мають позначку «Умовно¹».

¹ Повідомлення про помилку згадує лише `created_at`, `stored_at` та `q`, але умову задовольняють також `number`, `dependency_id` та `id`. Інші фільтри (`parent_id`, `user_id`, `queue_id`, `cause` тощо) умови **не** задовольняють.

> **Увага.** Перевіряється лише наявність параметра, а не його коректність: `created_at: {}` або `stored_at` з однією межею проходять валідацію. Але `stored_at` у SQL діє лише за обох меж, тож такий запит без інших обмежень призведе до повного сканування. Завжди задавайте обидві межі `created_at` (або принаймні `from`). Часове обмеження доступу з кроку 2 застосовується вже після валідації.

Позначення в колонці «Тип відповідності»: **Exact** — точний збіг; **ILIKE** — регістронезалежний шаблонний пошук; **Regex** — регулярний вираз; **Array** — масив (OR); **Range** — діапазон (включний); **Contains** — вкладення JSONB; **Tri-state** — `true` / `false` / не задано.

#### Пагінація, сортування, проєкція

| Параметр | Тип | Обов'язковий | Відповідність | Опис та значення за замовчуванням |
|---|---|---|---|---|
| `page` | `int32` | Ні | — | Номер сторінки, починаючи з 1. За замовчуванням — перша сторінка |
| `size` | `int32` | Ні | — | Розмір сторінки. За замовчуванням — **40**, максимум — **20 000** |
| `sort` | `string` | Ні | — | Назва колонки з префіксом `+` (за зростанням) або `-` (за спаданням), наприклад `-created_at`. У URL `+` кодується як `%2B`. Якщо не задано — `-created_at` (спершу найновіші) |
| `fields` | `string[]` | Ні | — | Проєкція полів відповіді. Якщо не задано — повертаються всі поля. Зменшує обсяг відповіді та вартість запиту |

#### Час і тривалість

| Параметр | Тип | Обов'язковий | Відповідність | Опис та значення за замовчуванням |
|---|---|---|---|---|
| `created_at` | `FilterBetween` | Умовно¹ | Range | Час створення виклику, epoch мс (UTC). Допускається одна межа. Найважливіший фільтр для продуктивності (відсікання чанків). Для користувачів із time-limited доступом до записів нижня межа піднімається до `зараз − period_to_playback_records` днів |
| `answered_at` | `FilterBetween` | Ні | Range | Час відповіді. **Застосовується лише якщо задано обидві межі** (`from` і `to`); інакше ігнорується |
| `stored_at` | `FilterBetween` | Умовно¹ | Range | Час запису в історію. **У SQL діє лише за обох меж**, хоча валідацію проходить і з однією. Зручно для інкрементальної синхронізації |
| `duration` | `FilterBetween` | Ні | Range | Загальна тривалість, с (`hangup_at − created_at`). Межа `0` або відсутня — ігнорується |
| `talk` | `FilterBetween` | Ні | Range | Час розмови (`talk_sec`), с, без урахування дзвінка та утримання |

#### Текстовий пошук і значення полів

| Параметр | Тип | Обов'язковий | Відповідність | Опис та значення за замовчуванням |
|---|---|---|---|---|
| `q` | `string` | Умовно¹ | ILIKE / Exact | Регістронезалежний пошук (`ILIKE`) за `destination`, `from_number`, `to_number` **або** точний збіг з ID виклику. Символ `*` замінюється на `%`; префікс і суфікс автоматично **не** додаються: `380*` — за початком, `*567` — за закінченням, `*380*` — за входженням, без `*` — повний збіг. Символи `%` та `_` також діють як шаблонні. Для колонок пошуку існують індекси |
| `number` | `string` | Умовно¹ | Regex | Значення перетворюється на регулярний вираз і зіставляється з номером пошуку (`search_number`) або з `destination`, `from_number`, `to_number`. Знаходить номер з будь-якого боку виклику. Підтримується триграмним індексом |
| `agent_description` | `string` | Ні | ILIKE | Нотатка агента до спроби черги **або** будь-яка анотація виклику. Як і в `q`, `*` замінюється на `%`; префікс/суфікс автоматично не додаються (для пошуку за входженням — `*текст*`) |
| `fts` | `string` | Ні | Full-text | Повнотекстовий пошук у транскрипціях (`plainto_tsquery`: усі слова, порядок не важливий). Неявно вимагає наявності транскрипції; ігнорується, якщо `has_transcript = false` |
| `variables` | `map<string,string>` | Ні | Contains | Виклики, змінні яких містять **усі** задані пари ключ–значення (точний збіг, чутливий до регістру). Для фільтра існують індекси |
| `tags` | `string[]` | Ні | Array | Виклики, що мають принаймні один із тегів |

## 2. Пояснення та архітектура (Explanation)

### 2.1. Концепції домену

**Плече виклику (Leg A / Leg B).** Один дзвінок складається з кількох плечей:

- **Leg A** — вхідне або вихідне плече верхнього рівня (`parent_id` порожній): абонент, який телефонує, або зовнішній напрямок, який набирає платформа.
- **Leg B** — дочірні плечі (`parent_id` вказує на Leg A): з'єднання з оператором, наступним оператором, зовнішнім номером тощо. Кожне переведення створює нове плече.

Дерево плечей зв'язують `parent_id`, `transfer_from`, `transfer_to` та `bridged_id`. Для швидкого отримання всього дерева використовуйте `dependency_id`, для хронології — разом із `timeline = true`.

**Статус завершення (`hangup_disposition`)** — похідна класифікація результату виклику. Обчислюється для плечей верхнього рівня; для дочірніх плечей — порожній рядок.

| Значення | Коли встановлюється |
|---|---|
| `not_answered` | Причина `USER_BUSY` або `NO_ANSWER` |
| `cancelled` | `ORIGINATOR_CANCEL`; `NORMAL_UNSPECIFIED` із результатом AI-AMD; `LOSE_RACE` у чергах типу 4 |
| `ended` | Завершено платформою (`hangup_by = F`) |
| `agent_dropped` | `NORMAL_CLEARING`, і розмову завершив оператор (вихідний виклик, завершений стороною A оператором; вхідний — стороною B після з'єднання; вихідний у чергах типів 4, 5, 1 — стороною B після з'єднання) |
| `client_dropped` | `NORMAL_CLEARING` в інших випадках — завершив клієнт |
| `error` | Решта причин |

**Часові метрики.**

```
created_at ──► answered_at ──► bridged_at ──────────► hangup_at
   │◄── wait_sec ──►│◄───────── bill_sec ──────────────►│
   │◄──────────────────── duration ───────────────────►│
                         (talk_sec = розмова без hold та дзвінка)
```

| Метрика | Формула / зміст |
|---|---|
| `duration` | `hangup_at − created_at` — повна тривалість, включно з дзвінком |
| `wait_sec` | `answered_at − created_at`; якщо не відповіли — `hangup_at − created_at` |
| `bill_sec` | `hangup_at − answered_at`; `0`, якщо не відповіли |
| `hold_sec` | Сумарний час утримання |
| `talk_sec` | Чистий час розмови (без дзвінка та утримання) |

**Історія черги проти історії агента.** Запис у `cc_calls_history` описує канал (плече) виклику. Дані про перебування в черзі (`joined_at`, `leaving_at`, `queue_wait_sec`, `queue_duration_sec`, `reporting_sec`, `result`, `form_fields`) надходять зі **спроби черги** (`attempt_id`), а `agent` / `team` — з агента, що її обробляв. Тому:

- `queue_wait_sec` описує очікування **в черзі**, а `wait_sec` — очікування **виклику** до відповіді;
- виклик без черги (внутрішній або прямий) матиме порожні поля спроби;
- фільтр `agent_id` працює за переліком агентів усіх плечей (`agent_ids`), а `user_id` — за користувачами плеча та учасниками (`user_ids`).

### 2.2. Механіка фільтрації та обмеження БД

**Обов'язковий якірний фільтр і часові межі.** API вимагає хоча б один із фільтрів `created_at`, `stored_at`, `number`, `q`, `dependency_id` або `id` (див. [1.3](#обовязкова-умова-пошуку)). Проте лише `created_at` дозволяє відсікати чанки гіпертаблиці. Запит, що задовольняє умову лише за `q`, `number` чи `id` без `created_at`, проходить по всіх чанках домену й може завершитися таймаутом. Практичне правило: завжди задавайте `created_at.from` та `created_at.to`.

> `cc_calls_history` зберігається як гіпертаблиця TimescaleDB з чанкуванням за `created_at`. Діапазон `created_at` дозволяє відсікати непотрібні чанки, тому він є найвпливовішим фільтром для продуктивності. Запит без нього сканує всі чанки домену.

**Особливості застосування фільтрів:**

| Фільтр | Особливість |
|---|---|
| `answered_at`, `stored_at` | Застосовуються лише за **обох** задених меж |
| `created_at` | Приймає одну межу (відкритий діапазон) |
| `duration` | Межа `0` ігнорується |
| `missed` | `false` рівнозначний відсутності фільтра |
| `timeline` | Потребує `dependency_id` |
| `fts` | Неявно вимагає наявності транскрипції; з `has_transcript = false` ігнорується |
| `rated` та фільтри балів | Будь-який із `rated_user`, `rated_by`, `score_*` обмежує вибірку оціненими викликами |
| `direction` / `directions` | Працює лише `direction` |

**Правила текстового пошуку.**

- `q` — `ILIKE` за `destination`, `from_number`, `to_number` і точний збіг за `id`. Перед виконанням символ `*` замінюється на `%` (`ReplaceWebSearch`); префікс і суфікс **не** додаються автоматично. Приклади: `380501*` — за початком, `*4567` — за закінченням, `*4567*` — за входженням, `380501234567` — повний збіг. Символи `%` та `_`, введені користувачем, не екрануються й також діють як шаблонні.
- `number` — регулярний вираз (`~`) з нормалізацією `GetRegExpQ()`. Для виразу `coalesce(search_number, cc_array_to_string(array[destination, from_number, to_number], '|'))` створено функціональний GIN-триграмний індекс, тому це найшвидший текстовий фільтр. Дуже короткі шаблони дають мало триграм, тож відсікання індексом стає менш ефективним.
- `agent_description` — `ILIKE` за нотаткою спроби та анотаціями (виконується підзапитами). Застосовується те саме правило: `*` → `%`, без автоматичного префікса/суфікса.
- `fts` — `to_tsvector(transcript) @@ plainto_tsquery(...)`: вектор обчислюється під час запиту, тож пошук по широкому діапазону дорогий.
- Мінімальної довжини рядка пошуку немає. Індекси існують для `number` (функціональний GIN-триграмний), для колонок пошуку `q` та для `variables`. Для `fts` вектор обчислюється під час запиту, для `agent_description` використовуються підзапити.

### 2.3. Оптимізація та продуктивність

**Рекомендовані комбінації фільтрів (від найшвидших):**

1. `created_at` (діапазон до 1 доби) + `queue_id` / `agent_id` / `user_id` + `skip_parent = true`.
2. `created_at` + `direction` + `cause` / `missed` — для звітів про пропущені та неуспішні виклики.
3. `id` / `parent_id` / `dependency_id` — точкові запити (розкриття одного виклику).
4. `stored_at` (обидві межі) — інкрементальне вивантаження новоствореної історії.

**Рекомендації:**

- **Використовуйте `fields`.** Подання `cc_calls_history` формує багато вкладених даних (файли, утримання, анотації, транскрипції, форми, метрики якості). Проєкція виконується на рівні SQL-запиту, тому запит лише потрібних полів зменшує і обсяг відповіді, і вартість виконання.
- **Тримайте `size` помірним.** За замовчуванням — 40, максимум — 20 000; для вивантажень зазвичай достатньо 100–1000. Ітеруйте сторінки до `next = false`.
- **Уникайте поєднання широкого діапазону з `fts` та `agent_description`** — вони виконуються підзапитами або обчисленнями під час запиту. Фільтри `number`, `q` та `variables` підтримуються індексами й значно дешевші.
- **Не покладайтеся лише на `q`/`number`/`id`.** Формально це дозволений якірний фільтр, але без `created_at` пошук проходить по всіх чанках. Додавайте часовий діапазон.
- **Для `dependency_id`** виконується рекурсивний обхід дерева — застосовуйте його лише до одного кореня.
- **Для вивантажень** розбивайте період на добові (або менші) вікна та обробляйте їх послідовно.

**Що робити при таймауті (`500`, `context deadline exceeded`) або надто великій вибірці:**

1. Звузьте `created_at` до меншого вікна (година/доба).
2. Додайте обмежувальний фільтр за сутністю: `queue_id`, `agent_id`, `user_id`, `gateway_id`.
3. Приберіть дорогі фільтри або застосуйте їх на вужчому діапазоні.
4. Зменште `size` та задайте `fields`.
5. Для регулярного вивантаження використовуйте `stored_at` (обидві межі) та запам'ятовуйте останню оброблену мітку.

Таймаут клієнта (HTTP-клієнт, reverse proxy) має бути не меншим за серверний, який задається налаштуваннями сервісу й може становити кілька хвилин. Інакше з'єднання буде розірване раніше, ніж сервер поверне відповідь.

## 3. Практичні приклади (Practical Examples)

У прикладах використано змінні: `{HOST}` — адреса API, `{TOKEN}` — токен сесії. Значення `int64` у відповіді повертаються рядками. Автентифікація — заголовок `X-Webitel-Access`.

### Сценарій 1. Пропущені виклики черги за добу

Мета: отримати вхідні виклики черги `12`, які не були з'єднані з оператором, за 29.09.2026 (UTC).

**cURL (GET)**

```bash
curl -G "https://{HOST}/api/calls/history" \
  -H "X-Webitel-Access: {TOKEN}" \
  -H "Accept: application/json" \
  --data-urlencode "created_at.from=1790640000000" \
  --data-urlencode "created_at.to=1790726399999" \
  --data-urlencode "queue_id=12" \
  --data-urlencode "direction=inbound" \
  --data-urlencode "missed=true" \
  --data-urlencode "skip_parent=true" \
  --data-urlencode "sort=-created_at" \
  --data-urlencode "size=20" \
  --data-urlencode "fields=id" \
  --data-urlencode "fields=created_at" \
  --data-urlencode "fields=from" \
  --data-urlencode "fields=queue" \
  --data-urlencode "fields=wait_sec" \
  --data-urlencode "fields=cause" \
  --data-urlencode "fields=hangup_disposition"
```

**JSON Request Payload (еквівалент для POST)**

```json
{
  "page": 1,
  "size": 20,
  "sort": "-created_at",
  "fields": ["id", "created_at", "from", "queue", "wait_sec", "cause", "hangup_disposition"],
  "created_at": { "from": 1790640000000, "to": 1790726399999 },
  "queue_id": [12],
  "direction": "inbound",
  "missed": true,
  "skip_parent": true
}
```

**JSON Response Payload**

```json
{
  "next": false,
  "items": [
    {
      "id": "0e6f8f3a-5b1c-4c1e-9a55-3f0f2b6c9d10",
      "created_at": "1790676900000",
      "from": { "type": "number", "number": "380501234567", "id": "", "name": "" },
      "queue": { "id": "12", "name": "Підтримка" },
      "wait_sec": 18,
      "cause": "ORIGINATOR_CANCEL",

  ]
}
```

Клієнт скинув виклик через 18 с очікування (`wait_sec`), не дочекавшись оператора.
